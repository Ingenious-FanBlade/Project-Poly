## 1. 职责

构建与测试系统为战斗垂直切片提供可追溯的 Windows x64 构建，以及从规则到实际运行程序的分层验证。它负责明确构建输入、执行条件、验证结果和失败证据，使一次构建或测试能对应到具体的 Unity 项目状态。

- **构建管理**：指定 Unity 版本、目标平台、参与构建的场景和项目配置；记录每次构建的输入、结果、日志及产物。正式战斗入口场景确定后，须显式纳入构建配置。
- **验证组织**：分别检查项目导入与编译、脱离表现的战斗规则、Unity 场景与交互集成，以及 Windows 玩家程序的基本可运行性。各层记录自身结果；未执行的必需检查不能视为通过。
- **失败定位**：将失败关联到源码版本、构建配置、测试用例和运行环境。涉及随机或连锁效果的战斗失败应保留足以复现的初始状态、输入顺序与随机信息。
- **职责边界**：具体玩法预期由相应 GDD 和战斗系统 TDD 定义；构建与测试系统负责执行验证并报告观察结果。规则状态由战斗系统提交，UI、动画和表现事件仅作为集成验证对象。

目前仓库只有模板场景和项目配置，尚无正式玩法代码、自动化测试套件、构建脚本或 CI 流程。本节及以下第 2–4 节描述目标设计，不表示这些能力已经实现；`Assets/Scenes/SampleScene.unity` 不能充当战斗垂直切片的验收场景。

## 2. 设计约束

- **引擎与平台**：使用 Unity 6000.6.1f1 和 URP；本里程碑的玩家构建目标先限定为 Windows x64。构建时核对编辑器版本、包依赖锁定文件、项目设置、场景清单及资源和对应 `.meta` 文件。
- **构建输入可追溯**：每次构建和测试记录源代码版本与工作区是否含未提交改动，避免把不同输入的结果合并判断。构建产物和报告应能追溯到同一次输入与配置；这里不要求不同机器生成逐字节相同的可执行文件。
- **场景显式指定**：玩家构建只使用经确认的场景清单。当前 `EditorBuildSettings` 中启用的 `SampleScene` 是模板，正式入口及所需场景尚待战斗垂直切片实现时确定。
- **规则可独立验证**：战斗规则的结果不依赖动画播放速度或 UI 帧率。出牌提交前的复验和每个原子效果结算都以最新 `BattleState` 为准；测试应能观察已提交状态、`EffectResult` 及其后发布的表现事件。
- **随机与顺序可复现**：使用战斗提供的可复现随机源；相同初始状态、命令顺序及随机种子应得到相同的规则结果和效果顺序。测试记录需要保留随机种子及必要的随机流位置、命令和效果顺序，供失败重现。
- **结果不可混淆**：命令拒绝、正常的零变化效果（如推拉受阻）、测试断言失败和构建／运行错误须分别报告。测试跳过或未运行不能计为通过。
- **仓库边界**：资源及 `.meta` 文件共同受版本控制，并遵守 Git LFS 规则；`Library/`、`Temp/`、`Logs/`、`UserSettings/` 和 IDE 生成文件不作为源码或提交产物。

## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| 构建配置（BuildProfile） | 一组明确的构建输入选择，包括引擎版本、平台、构建场景与开发／交付用途。它描述“准备构建什么”，不代表某次构建已经成功。 |
| 输入快照（SourceSnapshot） | 一次构建或测试所依据的仓库版本、工作区状态及项目输入标识。工作区有未提交改动时，须记录足以重建该输入的变更内容，才能判断两次结果是否来自同一输入。 |
| 构建记录（BuildRun） | 一次实际构建尝试及其结果，关联构建配置和输入快照，并保存日志与产物位置。失败尝试也应留有记录。 |
| 编辑器规则验证 | 在无需战斗动画和玩家程序的环境中验证领域规则与应用层编排，重点检查最新状态复验、费用与卡牌去向、棋盘索引、状态修正、效果连锁和确定性。 |
| Unity 集成验证 | 在 Unity 运行环境中检查场景装载、资源引用、输入与 UI、状态提交后的表现事件，以及规则结果与动画速度的隔离。 |
| 玩家程序冒烟验证 | 对已生成的 Windows x64 程序检查启动、进入战斗垂直切片及一段最短可完成流程；具体流程随正式场景和玩法实现确定。 |
| 战斗复现用例（BattleReplayCase） | 用固定初始状态、命令序列和随机信息重放一段战斗，比较最终状态与有顺序的规则结果。它是测试输入，不暗示已有完整玩家回放功能。 |
| 验证记录（TestRun） | 一次测试或检查的执行结果，记录所用输入、运行环境、通过／失败／跳过情况及失败证据；玩家程序检查还关联对应构建记录。 |

验证顺序原则上从项目导入与编译，推进到编辑器规则验证、Unity 集成验证、构建和玩家程序冒烟验证。具体执行工具、自动化方式与 CI 平台在后续章节和实现阶段确定。

## 4. 数据模型

下表定义构建与测试记录至少需要表达的信息；字段是概念约定，不指定 C# 类型、序列化格式、文件目录或 CI 服务。实现时可拆分或合并记录，但必须保留关联关系与失败复现所需的信息。

| 记录 | 核心字段 | 约束与用途 |
| --- | --- | --- |
| `BuildProfile` | `profileId`、`unityVersion`、`targetPlatform`、`architecture`、`renderPipeline`、`scenePaths`、`development` | 本里程碑目标值为 Unity 6000.6.1f1、Windows、x64、URP；`scenePaths` 必须是明确的构建场景清单，不能由模板场景默认推断。 |
| `SourceSnapshot` | `snapshotId`、`revision`、`hasLocalChanges`、`inputFingerprint`、可选 `localChangesRef` | `inputFingerprint` 覆盖包锁定文件、项目设置、场景、资源及 `.meta` 等实际输入；含本地改动时保留可重建改动的引用。仅凭提交号或改动标记不能断言输入相同。 |
| `BuildRun` | `buildId`、`profileId`、`snapshotId`、`startedAt`、`finishedAt`、`status`、`artifactRef`、`logRef` | 一次尝试只关联一个配置和输入快照；成功时记录产物位置，失败时记录可定位的错误日志。 |
| `TestCase` | `caseId`、`level`、`requirementRef`、`fixtureRef`、`expectedResult` | 标识规则、Unity 集成或玩家程序检查及其预期。`requirementRef` 指向相应 GDD／TDD 条目，避免测试只验证实现细节。 |
| `BattleReplayCase` | `replayId`、`initialStateRef`、`orderedCommands`、`randomSeed`、可选 `randomStreamPosition`、`expectedState`、`expectedOrderedEffects` | 作为战斗规则用例的固定输入与预期；从初始状态完整重放时可省略随机流位置，从中途重放时则需记录。结果比较覆盖关键状态及有序效果，不依赖动画时长。 |
| `TestRun` | `runId`、`caseId` 或测试集标识、`snapshotId`、可选 `buildId`、`environment`、`startedAt`、`finishedAt`、`status`、`failureRef`、`reportRef` | 每次执行保留独立结果。`status` 至少区分通过、失败和跳过；没有执行记录的必需检查视为未运行，不能计为通过。玩家程序测试须关联被测构建，失败时保留日志与重现条件。 |

一个 `SourceSnapshot` 可以关联多次 `BuildRun` 和 `TestRun`；一份玩家程序验证记录只关联实际被测的 `BuildRun`，且两者的 `snapshotId` 必须一致。`BattleReplayCase` 可作为 `TestCase.fixtureRef` 指向的用例数据。后续确定存储格式时，应保持这些关联，不能以最新一次运行覆盖历史失败记录。
