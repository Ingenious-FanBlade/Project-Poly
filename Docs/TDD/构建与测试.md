## 1. 职责

构建与测试系统为战斗垂直切片提供可追溯的 Windows x64 构建，以及从规则到实际运行程序的分层验证。它负责明确构建输入、执行条件、验证结果和失败证据，使一次构建或测试能对应到具体的 Unity 项目状态。

- **构建管理**：指定 Unity 版本、目标平台、参与构建的场景和项目配置；记录每次构建的输入、结果、日志及产物。实施时把规划的唯一战斗场景显式纳入构建配置。
- **验证组织**：分别检查项目导入与编译、脱离表现的战斗规则、Unity 场景与交互集成，以及 Windows 玩家程序的基本可运行性。各层记录自身结果；未执行的必需检查不能视为通过。
- **失败定位**：将失败关联到源码版本、构建配置、测试用例和运行环境。涉及随机或连锁效果的战斗失败应保留足以复现的初始状态、输入顺序与随机信息。
- **职责边界**：具体玩法预期由相应 GDD 和战斗系统 TDD 定义；构建与测试系统负责执行验证并报告观察结果。规则状态由战斗系统提交，UI、动画和表现事件仅作为集成验证对象。

目前仓库只有模板场景和项目配置，尚无正式玩法代码、自动化测试套件、构建脚本或 CI 流程。本文描述目标设计，不表示这些能力已经实现；`Assets/Scenes/SampleScene.unity` 不能充当战斗垂直切片的验收场景。

## 2. 设计约束

- **引擎与平台**：使用 Unity 6000.6.1f1 和 URP；本里程碑的玩家构建目标先限定为 Windows x64。构建时核对编辑器版本、包依赖锁定文件、项目设置、场景清单及资源和对应 `.meta` 文件。
- **构建输入可追溯**：每次构建和测试记录源代码版本与工作区是否含未提交改动，避免把不同输入的结果合并判断。构建产物和报告应能追溯到同一次输入与配置；这里不要求不同机器生成逐字节相同的可执行文件。
- **验收输入一致**：含未提交改动的构建仅用于开发验证。里程碑验收使用干净提交；导入编译、规则测试、Unity 集成测试、Windows x64 构建和玩家程序冒烟检查须针对同一 `SourceSnapshot` 全部通过。
- **场景显式指定**：战斗垂直切片验收程序启动后直接进入战斗，计划以 `Assets/Scenes/BattleSlice.unity` 作为唯一随包场景和首场景。这只界定本里程碑的验收入口；其他游戏流程仍由对应 GDD 定义。当前 `EditorBuildSettings` 中启用的 `SampleScene` 是模板，不得由它代替该场景。正式场景资产尚未创建。
- **开发与验收构建分离**：规划 `BattleSlice-Dev` 与 `BattleSlice-Acceptance` 两份受版本控制的 Unity Build Profile，分别覆盖场景清单与所需 Player 设置，均只包含上述场景。开发配置为 Windows x64、Mono、Development Build；验收配置为 Windows x64、IL2CPP、关闭 Development Build。验收记录只接受后者的产物，批处理不能依赖编辑器当前的共享设置。
- **玩家验证环境**：Windows 10 21H1（build 19043）及更新版本或 Windows 11，x64 SSE2 CPU、8 GB 内存、支持 DirectX 11 feature level 11_0 的显卡与厂商驱动。8 GB 是本项目先采用的玩家验证基线，不等同于已经测得的正式发行最低内存需求。
- **规则可独立验证**：战斗规则的结果不依赖动画播放速度或 UI 帧率。出牌提交前的复验和每个原子效果结算都以最新 `BattleState` 为准；测试应能观察已提交状态、`EffectResult` 及其后发布的表现事件。
- **预演可独立验证**：暂选完成、最终确认前的卡面预演使用隔离副本试算状态订阅、出牌事务消息及其连锁。测试须分别观察预演输出与真实战斗状态，确认预演不改变状态层数、能力计数器、正式随机流、真实出牌 ID 和表现事件；最终确认仍按最新状态复验并正式结算。
- **随机与顺序可复现**：使用战斗提供的可复现随机源；相同初始状态、命令与选择响应顺序及随机种子应得到相同的规则结果和效果顺序。测试记录需要保留随机种子及必要的随机流位置、输入和效果顺序，供失败重现。
- **结果不可混淆**：命令拒绝、正常的零变化效果（如推拉受阻）、测试断言失败和构建／运行错误须分别报告。测试跳过或未运行不能计为通过。
- **仓库边界**：资源及 `.meta` 文件共同受版本控制，并遵守 Git LFS 规则；`Library/`、`Temp/`、`Logs/`、`UserSettings/` 和 IDE 生成文件不作为源码或提交产物。

## 3. 核心概念

| 概念 | 含义 |
| --- | --- |
| 构建配置（BuildProfile） | 一组明确的构建输入选择，包括引擎版本、平台、脚本后端、场景与开发／验收用途。实施时以 Unity Build Profile 资产保存，分别使用 `BattleSlice-Dev` 和 `BattleSlice-Acceptance`；目前尚未创建。 |
| 输入快照（SourceSnapshot） | 一次构建或测试所依据的仓库版本、工作区状态及项目输入标识。工作区有未提交改动时，须记录足以重建该输入的变更内容，才能判断两次结果是否来自同一输入。 |
| 构建记录（BuildRun） | 一次实际构建尝试及其结果，关联构建配置和输入快照，并保存日志与产物位置。失败尝试也应留有记录。 |
| 编辑器规则验证 | 在无需战斗动画和玩家程序的环境中验证领域规则与应用层编排，重点检查最新状态复验、费用与卡牌去向、棋盘索引、状态修正、效果连锁和确定性。 |
| Unity 集成验证 | 在 Unity 运行环境中检查场景装载、资源引用、输入与 UI、状态提交后的表现事件，以及规则结果与动画速度的隔离。 |
| 玩家程序冒烟验证 | 对已生成的 Windows x64 程序依次检查启动、进入战斗、经正式玩家交互入口出一张牌及完成战斗；具体遭遇内容随垂直切片实现确定。 |
| 战斗复现用例（BattleReplayCase） | 用固定初始状态、有序命令与选择响应、随机信息重放一段战斗，比较最终状态与有顺序的规则结果。它是测试输入，不暗示已有完整玩家回放功能。 |
| 验证记录（TestRun） | 一次测试或检查的执行结果，记录所用输入、运行环境、通过／失败／跳过情况及失败证据；玩家程序检查还关联对应构建记录。 |
| 验收记录（AcceptanceRecord） | 对同一干净输入快照的全部必需检查和构建结果作一次汇总判断，关联所依据的记录并给出通过或未通过原因。 |
| 必需检查集（RequiredCheckSet） | 版本化的验收范围。本里程碑使用 `battle-slice-v1`，每次验收必须覆盖第 10 节 `BS-01` 至 `BS-10`。`BS-11` 用于检查验收器自身，在检查集或汇总逻辑变更时运行。每组实施时固定具体用例 ID，新增或改变必需项时更新版本。 |

验证顺序从项目导入与编译，推进到编辑器规则验证、Unity 集成验证、构建和玩家程序冒烟验证。规则与集成测试采用项目已有的 Unity Test Framework 的 EditMode、PlayMode 运行方式；本地与 GitHub Actions 自托管 Windows 运行器使用同一批处理入口。具体脚本与工作流尚未建立。

## 4. 数据模型

下表定义构建与测试记录至少需要表达的信息；字段是概念约定，不限定最终 C# 类型。构建配置计划映射为 Unity Build Profile 资产；测试原始结果保留 Unity Test Framework 的 XML，输入、构建、检查及验收摘要使用 JSON，运行日志保留文本。实现时可拆分或合并记录，但必须保留关联关系与失败复现所需的信息。

| 记录 | 核心字段 | 约束与用途 |
| --- | --- | --- |
| `BuildProfile` | `profileId`、`unityVersion`、`targetPlatform`、`architecture`、`renderPipeline`、`scriptingBackend`、`scenePaths`、`development` | `BattleSlice-Dev` 为 Mono、Development Build；`BattleSlice-Acceptance` 为 IL2CPP、非 Development Build。两者均为 Unity 6000.6.1f1、Windows x64、URP，场景清单仅含 `Assets/Scenes/BattleSlice.unity`。 |
| `SourceSnapshot` | `snapshotId`、`revision`、`hasLocalChanges`、`inputFingerprint`、可选 `localChangesRef` | `inputFingerprint` 覆盖包锁定文件、项目设置、场景、资源及 `.meta` 等实际输入；含本地改动时保留可重建改动的引用。仅凭提交号或改动标记不能断言输入相同。 |
| `BuildRun` | `buildId`、`profileId`、`snapshotId`、`startedAt`、`finishedAt`、`status`、`artifactRef`、`logRef` | 一次尝试只关联一个配置和输入快照；成功时记录产物位置，失败时记录可定位的错误日志。 |
| `TestCase` | `caseId`、`level`、`requirementRef`、`fixtureRef`、`expectedResult` | 标识输入预检、导入编译、规则、Unity 集成或玩家程序检查及其预期。`requirementRef` 指向相应 GDD／TDD 条目，避免测试只验证实现细节。 |
| `BattleReplayCase` | `replayId`、`initialStateRef`、`orderedInputs`、`randomSeed`、可选 `randomStreamPosition`、`expectedState`、`expectedOrderedEffects` | `orderedInputs` 包含命令、每次 `choose()` 的暂选目标及最终确认或取消响应；从初始状态完整重放时可省略随机流位置，从中途重放时则需记录。结果比较覆盖关键状态及有序效果，不依赖动画时长。 |
| `TestRun` | `runId`、`caseId` 或测试集标识、测试集的 `caseResults`、`snapshotId`、可选 `buildId`、`environment`、`startedAt`、`finishedAt`、`status`、`failureRef`、`reportRef` | 每次执行保留独立结果；测试集须保留每个用例的结果。`environment` 至少标识 OS、Unity 版本，玩家冒烟另记录内存、GPU 与驱动。`status` 区分运行中、通过、失败、跳过和中止；无执行记录不能计为通过。 |
| `AcceptanceRecord` | `acceptanceId`、`snapshotId`、`profileId`、`requiredCheckSetRef`、`stageResults`、`result`、`reason` | `requiredCheckSetRef` 固定为本轮 `battle-slice-v1` 版本与具体用例清单；`stageResults` 对每项记录实际采用的 `TestRun`／`BuildRun` ID，或标记未运行及原因。预检失败时允许不存在构建记录；只有清单内全部检查通过才记为验收通过。 |

一个 `SourceSnapshot` 可以关联多次 `BuildRun` 和 `TestRun`；一份玩家程序验证记录只关联实际被测的 `BuildRun`，且两者的 `snapshotId` 必须一致。`AcceptanceRecord` 引用本次验收实际采用的运行记录，不能混用其他快照的通过结果。`BattleReplayCase` 可作为 `TestCase.fixtureRef` 指向的用例数据。后续确定存储格式时，应保持这些关联，不能以最新一次运行覆盖历史失败记录。

## 5. 运行流程

以下是目标验收流程，批处理入口和 GitHub Actions 工作流尚未建立。开发验证可运行单个阶段，但只有完整流程能形成通过的 `AcceptanceRecord`。

1. **固定输入**：选择 `BattleSlice-Acceptance`、`battle-slice-v1` 必需检查集和一个干净提交，创建 `SourceSnapshot`。核对 Unity 版本、包锁定文件、URP、项目设置、资源及 `.meta`，并确认唯一构建场景为 `Assets/Scenes/BattleSlice.unity`；模板场景不能替代它。输入不满足条件时留下预检 `TestRun`。
2. **导入与编译**：在指定 Unity 版本下导入项目并编译，以 `TestRun` 记录结果、错误和警告。导入或编译失败时停止本次验收的后续阶段；汇总时将缺少执行记录的阶段标为未运行，不生成通过结论。
3. **编辑器验证**：批处理入口以 `BattleSlice-Acceptance` Build Profile 分别启动 Unity Test Framework 的 EditMode 和 PlayMode 测试进程，将结果写为 XML，并生成各自的 `TestRun` JSON。检查 XML 中的实际用例 ID、数量、失败和跳过情况；命令退出码为 0 但执行了零个或漏掉必需用例时仍判失败。规则测试不依赖动画，Unity 集成测试验证场景与交互。
4. **构建玩家程序**：前述必需检查通过后，批处理入口用 Unity 命令行指定 `BattleSlice-Acceptance` Build Profile 构建 Windows x64 玩家程序，生成 `BuildRun` JSON，记录产物与构建日志。构建成功只说明产物已生成，不等于里程碑验收通过。
5. **玩家程序冒烟**：启动该 `BuildRun` 的真实 IL2CPP 产物，并仅在传入专用冒烟参数时自动执行固定遭遇，依次验证启动、进入战斗、出一张牌、完成战斗。冒烟驱动器须经过与正常玩家操作相同的选牌、选择目标和确认入口，不得直接调用规则结算来代替出牌；完成战斗以实际提交的战斗结束状态为准。玩家程序输出逐步 JSON 与成功／失败退出码；批处理入口据此生成关联 `buildId` 的冒烟 `TestRun`。遭遇内容尚待确定，不得以模板场景或虚构数据形成通过记录。
6. **汇总验收**：对固定的必需检查集逐项核对运行记录、干净输入和各阶段与产物的 `snapshotId` 一致性，形成 `AcceptanceRecord`。任一必需用例失败、跳过、缺失或输入不一致时，结论为未通过并标明原因；修复后以新的运行记录重新验收。

本地与 CI 调用同一 PowerShell 批处理入口。测试进程以 Unity 的 `-runTests` 分别执行 EditMode 与 PlayMode，并指定 `-activeBuildProfile`、`-testResults`、`-logFile`；测试调用不附加 `-quit`。构建进程同样以 `-activeBuildProfile` 指向受版本控制的验收配置，配合 `-build`、`-batchmode`、`-quit`，避免依赖编辑器上次使用的目标。CI 选用 GitHub Actions 的自托管 Windows x64 运行器，由 `main` 分支提交或针对该分支的手动运行触发；手动触发时须校验事件分支为 `main` 且检出提交与本次 `SourceSnapshot` 一致，未建立信任策略前不让外部 PR 在自托管运行器上执行。运行器预装 Unity 6000.6.1f1、Windows Build Support、有效许可、IL2CPP 所需的 C++ 工具链和 Windows SDK，并具备满足上述玩家验证基线的图形环境。真实窗口与输入冒烟在已登录用户的交互式桌面会话运行，不以 Windows 服务会话代替。工作流须先取得 Git LFS 资源，再执行各阶段并上传 XML、JSON、文本日志和构建产物；运行器、工作流及具体上传策略均待实施。

## 6. 状态与生命周期

| 对象 | 生命周期 | 规则 |
| --- | --- | --- |
| `SourceSnapshot` | 捕获 → 供本次运行引用 | 捕获后视为不可变。执行期间若项目输入变化，本次结果不能沿用原快照形成验收；应重新捕获，正式验收须在新快照上运行全部必需阶段。 |
| `BuildRun` | 运行中 → 成功／失败／中止 | 每次尝试使用新 `buildId`。仅成功的构建可供玩家程序冒烟；失败或中止的尝试保留日志，残留文件不能作为有效产物。 |
| `TestRun` | 运行中 → 通过／失败／跳过／中止 | 每次尝试使用新 `runId`；未启动则无通过记录。重跑不得覆盖此前失败记录，跳过和中止不能代替通过。 |
| `AcceptanceRecord` | 汇总 → 通过／未通过 | 根据明确引用的 `BuildRun` 和必需 `TestRun` 作判断。结果形成后不因后续重跑自动变化；新一轮验收创建新记录。 |

开发验证允许使用含本地改动的 `SourceSnapshot`，但其构建和测试结果不能转为里程碑验收结果。正式验收必须重新在干净提交上执行完整流程。构建产物、报告与失败日志按运行 ID 分开保存，防止不同尝试互相覆盖；具体存储位置和保留期限尚待确定。

## 7. 模块接口

下表是能力边界和信息契约，不预设已经存在对应 C# 类、命令行入口或 CI 任务。

| 交互 | 输入 | 输出与约束 |
| --- | --- | --- |
| 项目与版本控制 → 输入预检 | 仓库版本、工作区状态、`BuildProfile`、Unity 与包配置、场景和资源 | 创建 `SourceSnapshot` 和预检 `TestRun`；验收时拒绝含本地改动的输入，并报告缺失或不匹配项。 |
| 输入预检 → Unity 导入与构建能力 | 已固定的输入快照、`BattleSlice-Acceptance` 配置和 Windows x64 目标 | 导入／编译输出 `TestRun`；批处理构建显式指定 Build Profile 并输出 `BuildRun`，不读取当前编辑器的默认场景。 |
| 规则测试能力 → 战斗领域与应用层 | 固定的 `BattleState` 测试初态、有序命令与选择响应、可复现随机信息 | 读取提交后的状态、`EffectResult` 和有序规则消息；规则结果无需等待动画。测试入口不直接改写生产规则。 |
| Unity 集成测试能力 → 场景、输入和表现层 | 正式测试场景、输入步骤和预期规则结果 | 验证资源引用、交互、状态提交与表现事件顺序；输出独立 `TestRun`。 |
| 玩家程序检查能力 → 构建产物 | 成功的 `BuildRun`、固定遭遇 ID 与专用冒烟参数 | 同一非 Development 玩家程序仅在该参数存在时通过正式玩家交互入口自动执行冒烟步骤，核对实际战斗结束状态，输出逐步 JSON 与退出码；批处理入口据此生成 `TestRun` 并关联被测 `buildId`。该能力须包含在验收配置中，正常启动不进入自动冒烟模式。 |
| 结果汇总能力 → 验收记录 | 同一 `snapshotId` 的导入、规则、集成、构建与冒烟记录 | 检查必需阶段是否全通过及输入是否干净，输出可追溯的 `AcceptanceRecord`，不修改玩法状态。 |

命令行与配置的实施依据见 Unity 的 [Build Profile 文档](https://docs.unity3d.com/6000.6/Documentation/Manual/build-profiles.html)、[命令行构建文档](https://docs.unity3d.com/6000.6/Documentation/Manual/build-command-line.html)和[编辑器命令行参数](https://docs.unity3d.com/6000.6/Documentation/Manual/EditorCommandLineArguments.html)；玩家环境的前置条件见 Unity 的 [系统要求](https://docs.unity3d.com/6000.6/Documentation/Manual/system-requirements.html)及 [URP 要求](https://docs.unity3d.com/6000.6/Documentation/Manual/urp/requirements.html)；CI 运行方式见 GitHub 的[手动工作流说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)与[自托管运行器说明](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners?platform=windows)，窗口冒烟对交互会话的要求参照 Microsoft 的 [Session 0 说明](https://learn.microsoft.com/en-us/windows/win32/services/service-changes-for-windows-vista)。

## 8. 异常与边界情况

| 情况 | 处理与验收影响 |
| --- | --- |
| Unity 版本、包配置、目标平台或构建场景不匹配 | 预检失败并记录实际值；缺少正式战斗入口时不得回退到 `SampleScene` 获得通过结论。 |
| 资源缺失、`.meta` 或 GUID 引用损坏、LFS 资源未正确取得 | 导入或场景检查报错，标记对应阶段失败；修复后重新执行，不复用旧结果。 |
| 导入、编译、测试或构建中止／超时 | 记录已完成阶段与错误；中止不算通过，未运行的后续阶段不能补填成功。重试产生新的运行 ID。 |
| 执行过程中输入文件变化 | 当前快照失效；不得把变化前后的测试和构建记录汇总为同一次验收。 |
| 随机重放结果或效果顺序不一致 | 规则验证失败，保留初态、有序命令与选择响应、种子、必要流位置及首个分歧；不得通过调整动画速度掩盖差异。 |
| 推拉受阻、零位移或零生命变化 | 按规则的正常 `EffectResult` 判断预期，不把合法零变化误报为构建错误或命令拒绝。 |
| 构建成功但程序无法启动、出牌或完成战斗 | `BuildRun` 可保留成功状态，冒烟 `TestRun` 失败，里程碑验收未通过。 |
| 必需测试缺失、被跳过或报告不可读取 | 无法提供通过证据；验收未通过，并指出缺失的阶段或记录。 |
| 测试进程退出码为 0，但 XML 中零个测试或缺少必需用例 | 按 `battle-slice-v1` 的固定用例清单比对，标记对应 `TestRun` 失败，不把进程成功视为测试通过。 |
| 自托管运行器缺少 Unity 许可、Windows 构建模块、IL2CPP 工具链或图形环境 | 对应阶段不能执行，记录环境错误；不得以编辑器测试代替真实玩家程序冒烟。 |
| 固定遭遇尚未配置或冒烟参数未产生逐步报告 | 冒烟阶段未通过；不得用场景成功加载或程序退出码单独代替“出一张牌并完成战斗”的证据。 |

## 9. 调试和日志

- **构建链路**：预检、导入、编译、测试、构建和冒烟日志共同携带 `snapshotId`、`profileId`、阶段、运行 ID、Unity 版本及开始／结束时间。构建日志补充目标平台、场景清单、产物位置和错误；验收记录引用实际采用的运行 ID。
- **战斗失败复现**：规则测试在失败时保存用例 ID、初始状态引用、命令与每次选择响应的顺序、随机种子与必要流位置、预期和实际的状态及有序效果。可用战斗／回合、命令、`PlayId`、`effectId` 与父效果 ID 串联选择、提交和连锁；棋盘错误包含相关 `EntityId` 与格坐标。
- **结果分类**：将输入预检错误、导入／编译错误、测试断言失败、程序崩溃与正常规则结果分别标记。效果诊断区分请求值、状态修正值、实际状态变化和 `EffectResult.reason`，避免将零变化误认为未执行。
- **日志密度**：常规记录阶段摘要、状态变化与失败上下文；Hover、逐候选查询和每次规则消息的详细跟踪仅在调试开关下输出。日志与报告作为运行产物保存，不将 Unity 生成的 `Library/`、`Logs/` 等目录提交到仓库。
- **报告格式**：EditMode 与 PlayMode 保留 Unity Test Framework 的原始 XML；`SourceSnapshot`、`BuildRun`、各阶段 `TestRun` 与 `AcceptanceRecord` 使用 JSON；Unity 编辑器、构建和玩家程序日志保留文本。冒烟 JSON 至少记录 `buildId`、`snapshotId`、固定遭遇 ID、随机种子、启动／进入战斗／出牌／完成战斗各步结果、最终战斗结果和退出码。摘要 JSON 引用原始报告路径及 `battle-slice-v1` 检查集版本，失败时仍保存可读取的部分报告。

## 10. 测试计划

以下均为待实施的验证用例；仓库虽包含 `com.unity.test-framework` 包，目前尚无正式测试套件、构建脚本和验收场景。`battle-slice-v1` 的每次验收必须覆盖 `BS-01` 至 `BS-10`，其中编辑器测试组须在实施时绑定非空、固定的用例 ID 清单；XML 中漏跑、零测试、失败或跳过任何必需用例均不能通过。`BS-11` 检查验收器本身，应在检查集或汇总逻辑变化时通过，才能启用新版本。规则与棋盘用例依据相应战斗 TDD，具体测试数据待实施时确定。

| 检查组 | 阶段 | 关键用例与预期 | 主要证据 |
| --- | --- | --- | --- |
| `BS-01` | 输入预检、导入与编译 | 正确版本和完整资源可导入编译；错误 Unity 版本、缺失包／`.meta`、失效场景引用或只有模板场景的配置不能通过验收。 | 输入快照、预检与导入编译记录。 |
| `BS-02` | 卡牌命令与选择 | Hover 与正式检查均要求基础费用可支付；候选为空且未达到最少选择数时不能提交，取消与切换卡牌不消费；已达到最少选择数时仍可进入最终确认。确认时基础费用、回合、卡牌或目标失效应拒绝；重复确认不二次消费。 | 卡牌、费用、牌区与成功出牌记录的前后状态。 |
| `BS-03` | 卡面数值预演 | 暂选完成后以同一快照和选择重复预演，数值及监听顺序稳定；扣费、移牌和成功出牌消息的模拟连锁会影响后续效果时，卡面按已模拟的修正后请求值更新，例如伤害请求为 `12` 而实际扣血为 `0` 时显示 `12`。预演不消耗真实状态层数、能力计数器或随机流，不分配真实出牌 ID，也不发布真实消息或表现事件。改变选择或战斗状态后旧预演失效，最终确认重新复验；随机、隐藏或依赖未知结果的数值显示不确定。 | 预演数值／不确定标记、隔离前后状态与随机流对比、最终确认后的正式效果请求值及有序消息。 |
| `BS-04` | 出牌提交消息 | 扣费与移牌作为两个原子效果依次发布执行前消息并接受类型化修正；修正后费用不可支付或牌区请求无效时两项都不提交。成功时两项共同提交，依次发布扣费与移牌执行后消息及一次成功出牌消息，三条消息分发后才结算其连锁；内部失败不留半提交或成功记录。 | 有序规则消息、修正值、提交前后状态与 `PlayId`。 |
| `BS-05` | 原子效果与连锁 | `choose → damage → push` 按顺序执行；监听修正顺序稳定。零实际扣血的已执行 `DamageEffect` 仍可触发独立 `DrawEffect`，抽牌连锁在 `push` 前稳定；推拉受阻保留消费和受阻原因。 | 有序规则消息、`EffectResult`、状态快照与效果链 ID。 |
| `BS-06` | 流程互斥与战斗结束 | 选择暂停或效果连锁尚未稳定时拒绝新的玩家出牌；所有执行帧及连锁稳定后才判断胜败。 | 命令结果、执行帧顺序和战斗结束记录。 |
| `BS-07` | 棋盘和实体不变量 | 覆盖 `1×1`、`10×10` 与无效尺寸、边界坐标、同格多实体和单一占位；放置、移动、移除后位置与索引一致，失败操作无部分更新。实体生命与状态的关键变化按各自 TDD 约束检查。 | 棋盘／实体状态断言和失败坐标、实体 ID。 |
| `BS-08` | 确定性与表现隔离 | 相同初态、有序命令与选择响应、种子得到相同最终状态及有序效果；结算读取最新 `BattleState`，状态提交先于表现事件，改变动画速度不改变规则结果。 | `BattleReplayCase`、状态及效果顺序比较、事件顺序记录。 |
| `BS-09` | Unity 场景与交互 | 正式场景装载、资源引用和输入可用；UI 能完成 Hover、暂选、卡面预演、最终确认、取消与出牌；预演数值来自隔离试算，战斗状态显示来自已提交结果。 | Unity 集成 `TestRun` 与关键状态／界面观察。 |
| `BS-10` | Windows x64 构建与冒烟 | 对同一干净快照生成 Windows x64 IL2CPP 非 Development 程序；以版本化固定遭遇和种子启动，进入战斗、出一张牌并完成战斗。任何一步失败均不能验收。 | `BuildRun`、产物、逐步冒烟 `TestRun`。 |
| `BS-11` | 验收记录一致性 | 故意缺失、跳过或混入其他快照的一项结果时，`AcceptanceRecord` 必须未通过；完整且同源的记录才通过。 | 汇总所引用的运行 ID 与未通过原因。 |

具体规则用例以[卡牌与效果系统](战斗系统/卡牌与效果系统.md)、[棋盘与坐标系统](战斗系统/棋盘与坐标系统.md)的测试计划为细化依据。实体与状态系统的测试计划尚待补齐，不能把上表中的建议视为已落地测试。目标帧率和画面比例见[技术概览](技术概览.md)；性能验收环境与测量方法列在下节，确定前只记录观察值。

## 11. 开放问题

- 唯一战斗入口与随包场景路径、构建配置和冒烟执行方式已确定，但场景资产尚未创建。固定遭遇的棋盘尺寸与障碍、我方和敌方实体及初始状态、初始费用与手牌、获胜操作序列和随机种子由玩法设计提供，具体内容与数值待定；在这些输入落实前 `BS-10` 无法通过。
- 测试夹具、战斗状态快照和随机流信息的持久化格式、版本迁移与比对粒度尚未确定；需保证失败可重现，并避免把表现数据纳入规则结果比较。
- 构建产物、测试报告、详细日志的保存位置、保留期限与失败证据的共享方式尚未确定。
- 上述 Windows 玩家验证环境已选定；技术概览提出的 60 帧以上和 16:9 画面要求仍需确定性能测量场景、方法及正式发行最低配置，不能仅由一次冒烟结果推断。
